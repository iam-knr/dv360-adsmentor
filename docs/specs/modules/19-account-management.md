# Module 19: Account management (three-level access dashboard)

Status: draft v1, 2026-10-28. Owner session: P2-08 (spec). Build phases: P3-02 (foundation part: roles, password policy, lockout, bootstrap, `/manage` guard, section 7 tasks M19-01 to M19-04, M19-14) and the new session P3-02b (the `/manage` dashboard, tasks M19-05 to M19-13, M19-15, M19-16).
Origin: owner requirement of 2026-10-28 (Kailas): a separate dashboard to manage student access levels. The owner adds accounts with the student's email and a password the owner creates and shares by hand. Three levels: Super admin, Admin, User. An Admin can also add Users.
Inputs: `PROJECT.md` 5.13, `docs/decisions.md` (ADR-004, ADR-009, ADR-012, ADR-034 superseded, ADR-037, ADR-044 public repo rule, ADR-045 up to 25 students, new ADR-047), `modules/18-instructor-training-layer.md` (4.1, 4.2, 4.4, 4.10, 4.11), `modules/02-partner-level.md` (users and roles inside a sandbox), `docs/explore/02-partner-level.md` (DV360 Users page), `data-model.md` (2.4, 5.1), `routes.md` (2, 5.3, 7, 8.19), `validation.md` (USR, SIM), `design-system.md` (2.4 grid, 2.8 forms, 2.11 modal, 2.12 banner, 2.13 toast, 2.14 empty state), `conflicts.md` (RC-016, RC-047, RC-061, RC-063, RC-065).
Tags: nothing tagged = decided from the sources above. `[SIM]` = invented here (no DV360 reference exists for Adsmetor accounts). `Δ` = spec delta, repeated in section 8. Where a row of `conflicts.md` and this file disagree, the row wins (RC-068 to RC-075 below).

Terminology. In this file and in the UI the levels are **Super admin**, **Admin** and **User**. Older files call the same people owner or platform admin, instructor, and student. The mapping is in 4.1. Never write "student" or "instructor" as an enum value any more.

## 1. Scope and out-of-scope

### In scope
| Area | Notes |
|---|---|
| Role hierarchy | `SUPER_ADMIN`, `ADMIN`, `USER`; who can create, see, edit, disable, reset and delete whom |
| Accounts dashboard | Separate area `/manage/**`: accounts list, add account, CSV import, account detail, cohorts, access periods, audit log, settings |
| Credentials | Email plus a password chosen by the creator or generated by the app, shared by hand. Shown once. Forced change at first sign in (default on, can be turned off per account) |
| Cohorts | The "cohort" is the module 18 classroom under a friendlier name (RC-069). Capacity, owner admin, time zone, default access period |
| Access control | Account status, account access period (from and to), class access windows stay in module 18 |
| Security | argon2id, lockout, throttling, session policy, CSRF, role checks in middleware and in every action, row scoping, audit, public repo rules, threat list |
| Provisioning link | Creating a User account creates a sandbox through module 18; disable freezes it; delete archives it |
| Self service | Change own password. Sign out of all sessions |

### Out of scope (v1)
- Email sending of any kind (invite, reset link, notices). Credentials are shared by the owner or the admin by hand. Optional later: M19-17.
- Self sign-up, join codes for students, social login, SSO, two-factor sign-in (listed as a later hardening item, Q8).
- Payments, billing, plans and seats per account.
- The DV360 role screens inside a sandbox (`/users`, module 02). They are a different system (4.1).
- Multi-tenant "organisations" above Super admin.

### 2.4 M3 Import accounts (CSV)
Three steps in one page: **Upload**, **Check**, **Result**.
1. Upload: drop zone or file picker (`.csv`, 200 KB max, 200 rows max). Link **Download template** (`email,name,cohort,password`). Cohort selector "Default cohort" for rows with an empty `cohort`. Checkbox "Ask for a new password at first sign in" (default on).
2. Check (dry run, nothing saved): table with one row per CSV line: status (OK, Error), email, name, cohort, password (shown as `generated` or `provided`, never the value), message. Errors use the exact texts of ACC-050 to ACC-058. Summary banner "{k} accounts ready, {e} rows have errors". Buttons **Create {k} accounts** (creates the valid rows only) and **Fix file and upload again**.
3. Result: the one-time list of generated passwords (email, password) with **Download CSV** (`accounts-{yyyymmdd-hhmm}.csv`, the only copy) and **Copy all**, plus the list of rows that were skipped. Provided passwords are never echoed back.
Role is always User for imported rows. There is no `role` column. Any `role` column in the file is ignored with an info line.

### 2.9 M9 Settings
Super admin only. One card per group, **Save** per card, every save is audited (`POLICY_CHANGED`):

### 3.4 Scoping rules (row level, in the app layer)
Accounts are not tenant rows, so the sandbox RLS of data-model 2 does not apply. Scoping is done by one accessor, `scopedUsers(db, actor)`, in `lib/accounts/scope.ts`:
- `SUPER_ADMIN`: no filter.
- `ADMIN`: `WHERE appRole = 'USER' AND (ownerAdminId = :actorId OR cohortId IN (cohorts where the actor is ownerAdminId or a ClassroomMember with appRole ADMIN))`, plus the actor's own row for self actions.
- `USER`: nothing (the accessor throws).
`scopedCohorts(db, actor)` follows the same shape. An ESLint rule (`no-restricted-syntax`) forbids `db.user.*` and `db.classroom.*` calls outside `lib/auth/**` and `lib/accounts/**`, and a test scans for it. An id outside the scope returns the same "Account not found." as a missing id (ACC-022), never a 403, so ids cannot be probed.

## 4. Behaviour

### 4.1 Role model and mapping to existing roles
Three levels, strict hierarchy `SUPER_ADMIN > ADMIN > USER`.
| Level (enum) | Who | Can do (short) | Old name (module 18, data-model) | Module 18 area |
|---|---|---|---|---|
| `SUPER_ADMIN` | The owner (Kailas) and anyone the owner trusts | Everything. Creates Admins and Users, sees all, disables, transfers, resets, changes roles, edits policy. Cannot be deleted, only disabled. At least one active Super admin must exist (ACC-024) | `ADMIN` (platform admin) | `/sim/admin/**`, `/sim/instructor/**` for all classes, `/manage/**` all |
| `ADMIN` | A trainer or instructor | Creates, edits, disables, enables, resets and deletes only Users in their own cohorts. Cannot create Admins or Super admins. Sees only their own Users and their progress. Runs their classes (windows, clock, scenarios) | `INSTRUCTOR` | `/sim/instructor/**` own classes, `/manage/**` scoped |
| `USER` | A paying student | Signs in, works only in their own sandbox, changes own password | `STUDENT` | `/sim/scenarios`, `/sim/attempts`, `/sim/progress`, `/sim/me`, DV360 routes of the own sandbox |

Which names win (RC-068): `SUPER_ADMIN`, `ADMIN`, `USER` are the stored enum values of `AppRole` (DM). Session payload values are lowercase `super_admin`, `admin`, `user` (RC-016 convention kept). The words student and instructor stay only as plain English in text, and in `ClassroomMember`-level wording "student" means a member with role `USER`. The old `ADMIN` (platform admin) value is **not** the new `ADMIN`: the data migration for a database created before this change maps `STUDENT` to `USER`, `INSTRUCTOR` to `ADMIN`, and old `ADMIN` to `SUPER_ADMIN` (no production data exists yet, so the Phase 3 schema simply starts with the new values). Landing after sign in: `USER` to `/sim/welcome` or Overview (module 18 4.1), `ADMIN` to `/sim/instructor`, `SUPER_ADMIN` to `/manage/accounts`.

Two role systems stay separate (data-model 2.4):
| Layer | Values | Where it applies |
|---|---|---|
| Account level `User.appRole` (this module) | `USER`, `ADMIN`, `SUPER_ADMIN` | Which Adsmetor areas you can open and whom you manage |
| DV360 role `UserAccessGrant.role` (module 02) | `STANDARD`, `READ_ONLY`, `REPORTING_ONLY`, `PARTNER_CLIENT`, `CREATIVE`, `ADMIN` | Inside one sandbox, as on the DV360 Users page |

Default DV360 role per account level (unchanged from RC-047 and routes.md 2, only renamed): `USER` gets `STANDARD` on their own sandbox partner (a scenario may override, for example `READ_ONLY`); `ADMIN` and `SUPER_ADMIN` get DV360 `ADMIN` on every sandbox they may open (own cohorts for Admin, all for Super admin) through view-as or demo sandboxes. The DV360 `ADMIN` is a different enum (`DvRole`) from `AppRole.ADMIN`; the code must always say which one it means (`dvRole` and `appRole` field names, never a bare `role` in a service signature).

Ownership: a `USER` row has `ownerAdminId` (the Admin responsible) and `cohortId`. An `ADMIN` row has `createdById` (a Super admin) and no cohort. When a Super admin creates a User directly, `ownerAdminId` is the cohort's owner admin. The owner can also be a Super admin (a cohort run by the owner). `ownerAdminId` and the cohort owner are kept equal by the services, except after **Transfer ownership**, which moves both in one transaction.

### 4.2 Permission matrix
`SA` = Super admin, `AD` = Admin, `US` = User. `own` = only Users in the actor's own cohorts or with the actor as owner admin. `self` = the actor's own account. `-` = not allowed (server returns FORBIDDEN or "Account not found." per ACC-022). Every row is a Vitest table case (section 6.3).
| Action | SA | AD | US |
|---|---|---|---|
| Open `/manage/**` | yes | yes | - |
| Open `/manage/settings` and edit policy | yes | - | - |
| List and search accounts | all | own, plus self | - |
| View account detail and progress | all | own, plus self | self profile at `/sim/me` only |
| Create `SUPER_ADMIN` account | yes | - | - |
| Create `ADMIN` account | yes | - | - |
| Create `USER` account | yes, any cohort | yes, own cohorts | - |
| Import users by CSV | yes | yes, own cohorts | - |
| Edit name, notes, access period of a User | all | own | - |
| Edit name of an Admin or Super admin | all | self | self (name at `/sim/me`) |
| Move User between cohorts | all | own cohorts to own cohorts | - |
| Change role (promote, demote) | yes, not self | - | - |
| Transfer ownership of a User, an Admin's users, or a cohort | yes | - | - |
| Disable or enable a User | all | own | - |
| Disable or enable an Admin | yes | - | - |
| Disable or enable another Super admin | yes, never the last active one, not self | - | - |
| Unlock a locked account | all | own Users | - |
| Reset password of a User | all | own | - |

Rules behind the matrix:
1. **No self harm.** Nobody can disable, archive or change the role of their own account (ACC-023). Changing own password is always allowed.
2. **No escalation.** The role of a new or edited account is checked against the actor level server-side and the form value is never trusted (ACC-020, ACC-021). An Admin cannot change anyone's role.
3. **Last Super admin.** Any action that would leave no ACTIVE Super admin is refused (ACC-024). Implemented with a transaction that counts active Super admins under `SELECT ... FOR UPDATE` on the Super admin rows, so two concurrent disables cannot both pass.
4. **Admins are peers.** An Admin never sees another Admin, a Super admin, or Users of another Admin (ACC-022).
5. **Demotion and archive of an Admin** need a replacement owner for their Users and cohorts first (ACC-025); the dialog offers **Transfer to...** and does both in one step.

### 4.3 Account status state machine
Status is stored in `User.status` (`ACTIVE`, `DISABLED`, `LOCKED`, `ARCHIVED`). Archived is the delete state (RC-065); `LOCKED` is automatic.
| From | To | Trigger | Who | Side effects |
|---|---|---|---|---|
| (new) | `ACTIVE` | create | per matrix | membership, sandbox provisioning (User), audit |
| `ACTIVE` | `DISABLED` | Disable | per matrix | `sessionVersion + 1` (sessions end), `disabledAt`, sandbox frozen with `frozenReason = ACCOUNT` and clock paused (4.10) |
| `DISABLED` | `ACTIVE` | Enable | per matrix | sandbox unfrozen if the class window is open (else stays frozen by the window logic, `frozenReason` becomes `WINDOW`), `failedLoginCount = 0` |
| `ACTIVE` | `LOCKED` | failure threshold reached (default 5) | system | `lockedUntil = now + 15 min`, audit `ACCOUNT_LOCKED`; sessions are not ended (the password is not known to be compromised, only guessed at) |
| `LOCKED` | `ACTIVE` | `lockedUntil` passes (checked on the next sign in attempt and by the list query), **Unlock**, or **Reset password** | system, per matrix | `failedLoginCount = 0` |
| `LOCKED` | `DISABLED` | Disable | per matrix | as `ACTIVE` to `DISABLED` |
| `ACTIVE`, `DISABLED`, `LOCKED` | `ARCHIVED` | Delete (never for Super admin) | per matrix | `archivedAt`, sessions end, sandbox `ARCHIVED`, membership kept for history, email stays reserved |
| `ARCHIVED` | `DISABLED` | Restore | SA, owning Admin (Users) | sandbox back to `FROZEN` (`frozenReason = ACCOUNT`), then the actor can Enable |
| `ARCHIVED` | (row removed) | Purge | SA | sandbox data deleted; `AuditLog` rows keep a copy of the email in `payload` and `targetUserId` is set to null. No automatic purge in v1: RC-065 default is archive for 90 days after the course, delete on request |
Not allowed: `ARCHIVED` to `ACTIVE` directly; any change that would leave no active Super admin; disable or archive of the actor's own account.

### 4.4 Credentials, generated passwords and the one-time reveal
Policy (ACC-010 to ACC-012): 10 to 128 characters; at least 3 of 4 classes (lowercase, uppercase, digit, symbol); not equal to the email; does not contain the email's local part when that part has 4 or more characters; not in the bundled common-password list (`lib/auth/common-passwords.ts`, 1,000 entries, lower-cased compare). The minimum length can be raised in M9, never lowered under 10.

Generator (`generatePassword()` in `lib/auth/password.ts`): 16 characters, `crypto.randomInt` only, alphabet without look-alikes: upper `ABCDEFGHJKLMNPQRSTUVWXYZ`, lower `abcdefghijkmnopqrstuvwxyz`, digits `23456789`, symbols `-_.!@#`. At least one of each class, then a Fisher-Yates shuffle with `crypto.randomInt`. About 95 bits. The browser button calls a server action `generateAccountPassword()` that returns one value and stores nothing, so the strength rule lives in one place. The strength meter in the form uses the same `checkPassword()` function shared by client and server.

Hashing (`hashPassword`, `verifyPassword`, `needsRehash`): argon2id with `@node-rs/argon2`, parameters m = 19 MiB, t = 2, p = 1 (OWASP minimum, same as module 18 4.1), random 16 byte salt, PHC string stored in `User.passwordHash`. A bcrypt cost of at least 12 is the documented fallback if the native module fails to build on Vercel (decision at M19-02, same storage column, the PHC prefix says which). On a successful sign in, a hash with older parameters is replaced (`needsRehash`). Unknown email sign in still runs one dummy `verifyPassword` so response time does not reveal whether the email exists.

Plaintext handling rules (tested, section 6.3):
1. The plaintext exists in memory only: in the request that creates or resets it, in the action result, and in the browser state of the one-time modal.
2. It is never written to the database, the audit log (`payload` has an allowed-keys list), application logs, error reports, analytics, URLs, `localStorage`, `sessionStorage`, cookies, or query cache. The logger redacts any key matching `/pass(word)?|secret|token|hash/i`.
3. Action results that carry a password are sent with `Cache-Control: no-store`. The React state is cleared on modal close, on route change, and on `pagehide`.
4. The modal cannot be reopened. To share the password again the creator uses **Reset password**.
5. The creator is told to share it out of band. The text "Adsmetor does not send email" is visible at creation and reset.
6. Generated password CSVs (import, bulk reset) are built in the browser from the action response and downloaded once. Cells are formula-safe (prefixed with `'` when they begin with `=`, `+`, `-`, `@`; generated passwords can begin with `-`, so they are always quoted and prefixed).
7. `mustChangePassword` defaults to on for every new account and every reset. With it on, the first sign in goes to `/sim/me/password` before anything else, and the shared password stops working for anyone else as soon as the person changes it. Turning it off (per account, or the default in M9) means the person keeps the password the admin shared. The owner can do that to keep onboarding simple (RC-070); the form says "Anyone who knows this password can sign in."

### 4.5 Sign in, lockout and sessions
Sign in (`signIn(email, password)`, module 18 4.1, extended):
1. Normalise the email (trim, lower-case). Check the IP throttle (`AuthThrottle` key `ip:{sha256(ip)}`, 10 attempts per minute) and the email throttle (key `email:{sha256(email)}`, lock after the threshold). Too many: SIM-002 `Too many attempts. Try again in {n} minutes.` Because the email key exists for unknown addresses too, a locked unknown email behaves exactly like a locked real one.
2. Load the user. Unknown, `ARCHIVED`, or no `passwordHash`: run the dummy hash, count a failure, return SIM-001 `Incorrect email or password.`
3. Wrong password: count a failure (`failedLoginCount + 1`; at the threshold set `status = LOCKED`, `lockedUntil`), return SIM-001. A correct password during a lock still returns SIM-002.
4. Correct password, then check state in this order and return the matching message (the person has proven they own the account, so the message may be specific): `DISABLED` ACC-070; access period not started ACC-071; ended ACC-072. Super admins and Admins ignore the account access period (it applies to Users).
5. Success: `failedLoginCount = 0`, `lockedUntil = null`, `lastLoginAt = now`, rehash if needed, new `activeSessionId`. If the policy says single session for the role, the previous session becomes invalid because its `sid` no longer matches. Redirect: forced change page when `mustChangePassword`, else landing per 4.1.
6. Every outcome that is not a plain success is counted. Only `ACCOUNT_LOCKED` is written to the audit log (not every failure, to avoid noise and unbounded growth).

Session (Auth.js v5 JWT, cookie `__Secure-` prefix in production, httpOnly, secure, SameSite Lax, path `/`): claims `sub`, `appRole`, `sessionVersion`, `sid`, `iat`, `lastActive`. Checked in `requireUser()` on every server component, action and route handler (a database read by primary key, cached for 5 seconds per instance): user exists and status is not `DISABLED` or `ARCHIVED`; `sessionVersion` equal; `sid` equal when the policy is single session; `now - lastActive` under the idle timeout; `now - iat` under the absolute lifetime. `lastActive` is rewritten at most every 5 minutes. Defaults (AccountPolicy): User idle 8 h, absolute 12 h, single session on; Admin idle 8 h, absolute 24 h; Super admin idle 2 h, absolute 8 h. Failing any check sends the person to `/sim/session-expired?reason=idle|absolute|revoked|other-device` (message ACC-074 or ACC-075). Events that bump `sessionVersion`: password change or reset, disable, archive, role change, **Sign out everywhere**. Middleware (edge) only verifies the JWT signature and reads the role claim; the authoritative check is `requireUser()`.

### 4.6 Security design for a public repository with shared passwords
#### 4.6.1 Layers
| Layer | Control |
|---|---|
| Transport | HTTPS only (Vercel), HSTS, cookies `secure` |

#### 4.6.3 Dev and test safety
`AUTH_DEV_BYPASS` is ignored when `NODE_ENV=production` (build-plan 1.10) and the bypass user is a Super admin only in tests. Fixtures never hold a real person's email. Test passwords are generated per run by `generatePassword()` and are not committed.

#### 4.6.4 Seeding the first Super admin
`npm run db:bootstrap` (P3-02, `prisma/bootstrap/10-admin.bootstrap.ts`) reads `SEED_SUPER_ADMIN_EMAIL` and `SEED_SUPER_ADMIN_PASSWORD` (and optional `SEED_SUPER_ADMIN_NAME`, default `Super admin`). If no `SUPER_ADMIN` row exists it creates one with `mustChangePassword = true`, hashes the password with the production parameters, and prints only "Super admin created: {email domain redacted}". If one exists it does nothing, even when the variables changed (so a leaked or old env value cannot reset an existing account). Missing variables in production make the script exit with code 1 and a message that names the variable but never prints a value. The values live only in Vercel (Production and Preview) and in the owner's password manager. Names replace `SEED_ADMIN_EMAIL` and `SEED_ADMIN_PASSWORD` of build-plan 1.10 (RC-071).

### 4.8 CSV import
Format: UTF-8, header row `email,name,cohort,password` (comma separated, double-quote escapes, BOM allowed, CRLF or LF). `cohort` is the cohort name inside the actor's scope (an Admin: own cohorts; a Super admin: any, ambiguous names need `ownerAdmin:name`, shown as an error). `password` is optional: empty means generate; if present it must pass ACC-010 to ACC-012 and is never shown again. Limits: 200 KB, 200 data rows. Processing order: parse, per-row validation, duplicate check inside the file, existing-account check, capacity check per cohort (rows beyond capacity fail in file order), then (if `dryRun = false`) creation of the valid rows, each in its own transaction, followed by one provisioning enqueue per created User. Re-uploading the same file after a partial run reports the created rows as ACC-054 (idempotent, nothing is created twice). The audit log gets one `ACCOUNTS_IMPORTED` row with counts and the file name, never the content.
Exact row messages are ACC-050 to ACC-058 (4.9).

### 4.10 Link to sandbox provisioning (module 18)
- **Create User**: after the account transaction commits, call `enqueueProvisionSandbox(cohortId, userId)` (module 18 4.4 `provisionSandbox`, idempotent, unique `(classroomId, ownerUserId)`). If the call fails the account stays and the detail page shows Sandbox "NOT CREATED" with **Retry provisioning**. Admins and Super admins get no student sandbox; demo sandboxes are module 18's.
- **Disable**: sessions end; the sandbox goes `FROZEN` with `frozenReason = ACCOUNT` and its clock `PAUSED` (module 18 4.3 freeze helper, remembered state saved). The class window tick must skip sandboxes with `frozenReason = ACCOUNT` when unfreezing. Data is kept.
- **Enable**: the sandbox is unfrozen only if the class window is open; otherwise the normal window logic unfreezes it later.
- **Move cohort**: one transaction updates `User.cohortId`, the `ClassroomMember` row, `Sandbox.classroomId` and the denormalised `classroomId` columns (data-model 2.2: `SimDailyMetric`, `ChangeGroup`, `ScenarioAttempt`, `Notification`). The sandbox, clock and market seed (stored on the sandbox's own `SimClock`) are kept, so the user keeps their work. Attempts keep their scenario.
- **Delete (archive)**: sandbox `ARCHIVED`; data stays 90 days after the course (RC-065), purge on request by a Super admin (`purgeAccount`).
- **Reset password, role change** do not touch the sandbox.
- **Self service reset of sandbox** stays module 18 (`allowStudentReset`).

### 4.11 Audit log
Single table `AuditLog` (module 18 Δ18-10 plus Δ19-5). Written in the same transaction as the change. Actions: `ACCOUNT_CREATED`, `ACCOUNT_UPDATED`, `ACCOUNT_ROLE_CHANGED`, `ACCOUNT_DISABLED`, `ACCOUNT_ENABLED`, `ACCOUNT_LOCKED`, `ACCOUNT_UNLOCKED`, `ACCOUNT_COHORT_MOVED`, `ACCOUNT_OWNER_TRANSFERRED`, `ACCOUNT_ARCHIVED`, `ACCOUNT_RESTORED`, `ACCOUNT_PURGED`, `ACCOUNTS_IMPORTED`, `PASSWORD_RESET`, `PASSWORD_CHANGED`, `SESSIONS_REVOKED`, `COHORT_CREATED`, `COHORT_UPDATED`, `COHORT_ARCHIVED`, `POLICY_CHANGED`, `AUTHZ_DENIED` (a request refused by `can()` or scope, written with `result = DENIED`). `payload` holds an allowed-keys list only: `fromRole`, `toRole`, `fromStatus`, `toStatus`, `cohortId`, `fromCohortId`, `count`, `fileName`, `reason`, `mustChangePassword`, policy key names with old and new numeric values. No password, hash, secret or email body text. Retention 365 days; a daily job deletes older rows. `AuditLog` is append-only for the app role (no update or delete grants except the retention job).

## 6. Acceptance criteria

### 6.1 Numbered
**Roles and permissions**
1. A Super admin creates an Admin: the account exists with role `ADMIN`, no cohort, `mustChangePassword = true`, and an `ACCOUNT_CREATED` audit row.
2. An Admin creates a User in their own cohort: the User has `ownerAdminId` = the Admin, a membership in the cohort, and a provisioning job is enqueued.
3. An Admin cannot create an Admin or Super admin: the Role field is locked to User and a forged request returns ACC-020 and writes `AUTHZ_DENIED`.
4. An Admin never sees another Admin's Users, other Admins or Super admins in the list, search, filters, export, audit log or by id (ACC-022 for ids).
5. A User who opens `/manage` or `/manage/accounts/new` is sent to `/sim/forbidden`; an Admin who opens `/manage/settings` likewise. Direct action calls from a User session return FORBIDDEN.
6. The permission matrix of 4.2 holds for every action and level (table test).
7. Nobody can disable, archive or change the role of their own account (ACC-023). The last active Super admin cannot be disabled, demoted or archived (ACC-024), also under two parallel requests.
8. Super admin accounts cannot be deleted (ACC-026) but can be disabled when another active Super admin exists.
9. Demoting or archiving an Admin with Users needs `transferTo` (ACC-025); after the transfer the Users and cohorts belong to the new Admin.

**Credentials**
10. The Generate button returns a 16 character password that passes `checkPassword()`; it is shown with Show and Copy; after **Done** the modal cannot be reopened and no password is in the database, logs, audit rows or browser storage.
11. A typed password that fails ACC-010 to ACC-012 shows the message and blocks **Create account**.
12. A new account with "Ask for a new password" on is sent to `/sim/me/password` at first sign in; after the change the old shared password fails and other sessions end. With the toggle off the shared password keeps working and the person lands on their normal page.
13. Reset password (single and bulk) returns new secrets once, ends the person's sessions, clears a lock, and writes `PASSWORD_RESET` without the value.

**Sign in and sessions**
14. Unknown email, wrong password and an archived account all show `Incorrect email or password.`; five failures lock the account for 15 minutes (SIM-002); a locked unknown email shows the same lock text; a correct password during a lock is refused; **Unlock** and **Reset password** clear the lock; the lock ends by itself after 15 minutes.
15. A disabled User with the right password sees ACC-070 and has no session; an existing session ends on the next request.
16. A User outside their access period sees ACC-071 or ACC-072 after a correct password.
17. With single session on for Users, a second sign in ends the first session (ACC-074). Idle and absolute limits end sessions (ACC-075).
18. **Sign out everywhere** and password change end all other sessions.

**Dashboard**
19. The accounts list searches by name and email, filters by role, status, cohort (and owner admin for Super admin), sorts, and pages; bulk Disable, Enable, Reset password, Move cohort and Delete work for up to 100 rows and report skipped rows (ACC-060, ACC-062).
20. Delete asks for the typed `DELETE`, archives the account, ends its sessions, archives the sandbox, and keeps the email reserved; **Restore** returns it as Disabled.
21. Cohort capacity of 25 blocks the 26th User in the form, the import and **Move cohort** (ACC-032); a Super admin can raise it to at most 60 (ACC-034).
22. CSV import: a dry run lists per-row errors with the exact texts of ACC-050 to ACC-058 and saves nothing; confirming creates the valid rows only; generated passwords are offered once as a CSV; uploading the same file again reports every row as already existing.
23. Account detail shows last sign in, status, sandbox state with retry, and progress links; Disable freezes the sandbox without deleting data; Enable restores it when the window is open.
24. The audit log lists every action of 4.11, scoped by level; exports are formula safe; denied attempts appear as `Denied`.
25. Policy changes in M9 apply to new sessions and attempts and are audited; an Admin cannot open M9.

**Security**
26. `no-secrets` and `plaintext` tests pass: no tracked file holds a PHC hash, a real looking email outside `example.test` or `.invalid`, or a password value; no log line produced during the create, reset and import flows contains the plaintext.
27. Bootstrap creates a Super admin only when none exists, never changes an existing one, and exits with an error naming the missing variable in production.
28. State changing requests with a foreign `Origin` are rejected.

### Open questions for the owner (each has the default used in this spec)
- Q1. Should an Admin see only their own Users? **Default: yes** (own Users and own cohorts only; Super admin sees all). Changing it to "all Users of all Admins" is a change to `scopedUsers()` and the matrix.
- Q2. May every person change their own password? **Default: yes**, at `/sim/me/password`, with the current password required.
- Q3. How many Super admins at the start? **Default: one, the owner**, created by bootstrap from Vercel env values. A second one can be added later as a safety net.
- Q4. Forced password change at first sign in: **Default: on for new Users and Admins**, the creator can turn it off per account, and the owner can change the default in Settings. Turning it off means the shared password stays valid until someone resets it.
- Q5. One active session per account: **Default: on for Users, off for Admins and Super admins.** Turn off in Settings if two devices per student must work.
- Q6. Cohort size: **Default 25, hard maximum 60**, raised only by a Super admin (PROJECT.md says up to 25 concurrent students).
- Q7. Account access period as two columns on the account (`accessStartsAt`, `accessEndsAt`) instead of an `AccessWindow` row per account, because class windows already exist and one row per student would clutter that table. **Default used.** Tell us if you want a shared "access window" object that many accounts can point to.
- Q8. Email invites, reset links and two-factor sign in need a mail or SMS provider that is not in the stack. **Default: none in v1**, task M19-17 reserved. Which provider, if any, later?
- Q9. Email cannot be edited after creation (v1). **Default used**; a wrong email is fixed by deleting and re-creating the account.
- Q10. Data retention: archived accounts keep data 90 days and are purged only on request (RC-065 default). Confirm, together with Adsmetor legal.
- Q11. Should Admins be able to turn the forced password change off for their Users? **Default: yes.** If the owner wants to keep it mandatory for everyone but Super admin-created accounts, add a policy switch.
